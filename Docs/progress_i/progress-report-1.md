## 1. แรงบันดาลใจและที่มา

ร้านอัญมณีย่านบางมดเจอค่าเช่าที่ที่แพงขึ้นเรื่อยๆ จึงย้ายมาขายออนไลน์ แต่เจ้าของร้านยังอยากให้ลูกค้าได้ประสบการณ์เหมือนมาเลือกซื้อที่ร้านจริง และอยากใช้ระบบอัตโนมัติ 100% บรรจุอัญมณีลงบรรจุภัณฑ์ของขวัญเพื่อลดการจ้างพนักงาน

ทีมจึงออกแบบระบบเป็น 2 ฝั่งที่ทำงานต่อกัน:

1. **Storefront (ร้านเสมือน)** บน Meta Quest 3: ลูกค้าเดินในร้าน หยิบอัญมณีขึ้นมาหมุนดูได้ทุกมุม ใส่ตะกร้า จ่ายเงินด้วยบัตร และกดเรียกพนักงานมาคุยสดได้
2. **Packing Station (สถานีบรรจุจริง)**: แขนกล Dobot MG400 หยิบอัญมณีจริงตามรูปทรง (Cut) และสี (Color) ที่ลูกค้าสั่ง ใส่ลงถุงของขวัญบนสายพาน ปิดปากถุง แล้วส่งไปปลายสายพาน
3. **Remote maintenance (Teleop)**: ถ้ามีอัญมณีหล่นผิดที่ พนักงานซ่อมบำรุงใส่ Quest แล้วบังคับแขนกลตามตำแหน่งมือเพื่อหยิบกลับ

## 3. การวางแผนการทำงาน

### 3.1 กระบวนการทำงานของทีม

ทีมใช้ GitHub เป็นศูนย์กลาง (repo `LoveRobot-CPE494/JewelryShopCPE494_LoveRobot`) โดยรวมทุกส่วนไว้ใน monorepo เดียว:

```
Unity/JewelryShop/   Storefront บน Meta Quest 3 (C#)
Dobot/               Hub บน PC + การสั่ง MG400 (Python)
UNO/                 Firmware Arduino UNO (C++)
Docs/                โจทย์, ADR (บันทึกการตัดสินใจ), มาตรฐานโค้ด, bench test
```

ทุกงานเดินตาม pipeline เดียวกัน:

1. **Grill**: ซักถามประเด็นออกแบบให้ชัด แล้วบันทึกเป็น **ADR** (Architecture Decision Record) และศัพท์ใน `GLOSSARY.md`
2. **Spec**: เขียน spec ของฟีเจอร์เป็น GitHub Issue
3. **Ticket**: แตก spec เป็น ticket ย่อยที่มีลำดับก่อน-หลัง (`blocked_by`) และ priority P0/P1/P2
4. **Implement**: ทำทีละ ticket บน branch แยก
5. **Code review + Pull Request**: ไม่มีการ push ตรงเข้า `main`; ทุกอย่างผ่าน PR

> 📷 **ใส่รูป 3.1**: แคปหน้า GitHub Issues ที่เห็น spec/ticket พร้อม label (`area:unity`, `priority:P0` ฯลฯ)
> คำบรรยาย: "การแตกงานเป็น spec และ ticket บน GitHub Issues"

> 📷 **ใส่รูป 3.2**: แคปหน้า Pull Requests ที่ merge แล้ว (เห็นจำนวน PR ที่ merge แล้ว 40 PR)
> คำบรรยาย: "ทุกการเปลี่ยนแปลงเข้าสู่ main ผ่าน Pull Request"

## 4. ภาพรวมการออกแบบระบบ

### 4.1 สถาปัตยกรรม

![รูป 4.1 แผนผังการเชื่อมต่อระหว่าง Quest 3, PC Hub, MG400, Arduino UNO และ Staff Console](images/4-1-architecture.png)

*รูป 4.1: แผนผังการเชื่อมต่อระหว่าง Quest 3, PC Hub, MG400, Arduino UNO และ Staff Console (วาดด้วย archify; ต้นฉบับแบบโต้ตอบได้ที่ [`images/4-1-architecture.html`](images/4-1-architecture.html))*

หลักการสำคัญ (อ้างอิง ADR ใน `Docs/adr/`):

- **PC เป็น Hub กลาง (ADR-0001)**: Quest ไม่คุยกับ MG400/Arduino ตรงๆ เพราะ Unity บน Android/Quest เปิด Serial ไม่ได้, Dobot SDK มีให้ใน Python อยู่แล้ว และลำดับการบรรจุ (Packing Sequence) ควรอยู่ใน state machine เดียว PC ยังเป็นจุดเดียวที่บังคับ safety limit ของแขน (ขอบเขตพื้นที่, Z ต่ำสุด, จำกัดความเร็ว)
- **แบ่งหน้าที่ฮาร์ดแวร์ (ADR-0004)**: MG400 หยิบ-วาง + ดูด/ปล่อย และคุมสายพานกับเซนเซอร์หยุดถุงผ่าน I/O ของตัวเอง (สั่งจาก Python บน PC); Arduino UNO คุมแค่ servo ของ Bag Closer; ทั้งสองไม่สั่งกันเอง ทุกอย่างผ่าน PC → ทดสอบทีละระบบได้
- **Staff Call ต่อตรง Quest ↔ Staff Console (ADR-0010)**: ใช้ Unity Netcode for GameObjects เพราะทั้งสองฝั่งเป็น Unity project เดียวกัน ซิงก์ Avatar และเสียงได้แทบไม่ต้องเขียนโค้ดเอง Hub ดูแลเฉพาะ Packing Station
- **Checkout อนุมัติเมื่อ Hub รับ Order แล้วเท่านั้น (ADR-0012)**: "Approved" บนเครื่องรูดบัตรจึงหมายถึง Order ถูกส่งไปบรรจุจริง

### 4.2 ลำดับการทำงานเมื่อลูกค้าสั่งซื้อ (Packing Sequence)

1. ลูกค้าหยิบ Gem Model ใส่ **Order Tray** แล้วแตะ **Payment Card** กับ **Card Terminal**
2. Quest ส่ง Order (รายการ Cut + Color) ไป Hub → Hub ตอบรับ → เครื่องแสดง Approved + ออก Receipt
3. Hub สั่งสายพานผ่าน MG400 พาถุงของขวัญมาหยุดหน้าแขนกล (เซนเซอร์ต่อ I/O ของ MG400)
4. Hub สั่ง MG400 หยิบ Gem Piece จาก Stock Slot ที่ตรงกับ Cut + Color ทีละชิ้นด้วยหัวดูด ใส่ลงถุง
5. Hub สั่ง Arduino ให้ Bag Closer (servo) ปิดปากถุง แล้วสั่งสายพานผ่าน MG400 ส่งถุงไปปลายทาง

![รูป 4.2 ลำดับการบรรจุหนึ่ง Order](images/4-2-packing-sequence.png)

*รูป 4.2: ลำดับการสั่งงานระหว่าง Storefront, PC Hub, MG400 (สายพานและเซนเซอร์ผ่าน I/O) และ Arduino UNO ในการบรรจุหนึ่ง Order (วาดด้วย archify; ต้นฉบับแบบโต้ตอบได้ที่ [`images/4-2-packing-sequence.html`](images/4-2-packing-sequence.html))*

### 4.3 ระบบ Remote Maintenance (Teleop)

ใช้ **Controller ของ Quest 3** แทน hand tracking (ADR-0003) เพราะแม่นและนิ่งกว่า และมีปุ่มจริงสำหรับ deadman/หยุดฉุกเฉิน ตำแหน่ง Controller ยังถือเป็น "ตำแหน่งมือ" ตามเกณฑ์ 10 คะแนน

| Controller | MG400 |
|---|---|
| ตำแหน่ง (x, y, z) | ตำแหน่งปลายแขน (หลัง calibrate) |
| กด Grip ค้าง | ให้แขนตาม (Deadman), ปล่อยแล้วหยุดทันที |
| Trigger | ดูด / ปล่อย |
| A / B | กลับ Home / หยุดฉุกเฉิน |
| Thumbstick | ขยับขึ้น-ลงทีละน้อย |

> 📷 **ใส่รูป 4.3**: รูป Controller Quest 3 พร้อมลูกศรชี้ปุ่มแต่ละปุ่มตามตาราง
> คำบรรยาย: "การแมปปุ่ม Controller สำหรับโหมด Teleop"

### 4.4 ความปลอดภัย

- **ซอฟต์แวร์:** ทุกคำสั่งเคลื่อนที่ผ่าน safety proxy บน PC (ขอบเขตพื้นที่, Z ต่ำสุด, จำกัดความเร็ว, Deadman)
- **ไฟฟ้า:** E-stop จริงที่ตัดไฟสายพานและ servo; servo/มอเตอร์ใช้แหล่งจ่ายแยก ไม่ดึง 5V จาก UNO
- **ขั้นตอน:** มี checklist bench test (`Docs/standards/packing-station-bench-test.md`) ต้องผ่านทุกข้อก่อนสาธิตทุกครั้ง

> 📷 **ใส่รูป 4.4**: แคปหน้า checklist bench test หรือรูปปุ่ม E-stop จริงที่ติดตั้ง
> คำบรรยาย: "Checklist ความปลอดภัยก่อนการสาธิต"

## 5. การเปรียบเทียบอุปกรณ์

### 5.1 หัวจับของแขนกล (End effector): เลือก **Suction Cup** (ADR-0002)

| ตัวเลือก | ข้อดี | ข้อเสีย | ผล |
|---|---|---|---|
| **Suction cup + ปั๊ม/โซลินอยด์ (ต่อ DO ของ MG400)** | อัญมณีทั้ง Round และ Emerald มีหน้า table แบนด้านบนให้ดูด; ไม่ต้องหมุน J4 ให้ตรงด้านของ Emerald → สำคัญมากกับการหยิบของหล่นที่วางแบบสุ่ม | ถ้าอัญมณีคว่ำ/ตะแคงอาจดูดไม่ติด | เลือก |
| Electric gripper (เช่น DH-Robotics PGE) | แม่นยำ | แพง, ต้องหมุนให้ตรงก่อนจับ | ไม่เลือก |
| Gripper พิมพ์ 3D + servo ต่อ Arduino | ถูก | จับชิ้นเล็กลื่นได้ไม่มั่นคง, ต้องซิงก์เวลาข้ามบอร์ด | ไม่เลือก |

### 5.2 อุปกรณ์ควบคุมฝั่ง Teleop: เลือก **Quest 3 Controller** (ADR-0003)

| ตัวเลือก | ข้อดี | ข้อเสีย | ผล |
|---|---|---|---|
| **Controller** | tracking แม่น, มีปุ่มจริงสำหรับ Deadman และ E-stop | ต้องถือ Controller | เลือก |
| Hand tracking | ไม่ต้องถืออะไร | ไม่นิ่ง, ไม่มีปุ่มกายภาพสำหรับหยุดฉุกเฉิน | ไม่เลือก |

### 5.3 ตัวกลางเชื่อมระบบ: เลือก **PC (Python) เป็น Hub** (ADR-0001)

| ตัวเลือก | ข้อดี | ข้อเสีย | ผล |
|---|---|---|---|
| **PC Hub (Python)** | ใช้ Dobot SDK ได้, ต่อ Serial ได้, logic ความปลอดภัยอยู่ที่เดียว | ต้องเปิด PC และใช้ router ตอนสาธิต | เลือก |
| Quest ต่อ MG400 ตรง | ไม่ต้องมี PC | Quest ต่อ Arduino ไม่ได้, logic ความปลอดภัยอยู่ในแว่นที่หลุดการเชื่อมต่อได้ | ไม่เลือก |
| MG400 สั่ง Arduino ผ่าน DI/DO | ไม่ต้องมี PC | debug ยาก, ส่งข้อมูลได้น้อย | ไม่เลือก |

### 5.4 บอร์ดควบคุม Bag Closer (servo): **i-Duino R3B (UNO-compatible, ATmega328P)**

เทียบเฉพาะ 2 ตัวที่ทีมมีอยู่จริง

| ตัวเลือก | ข้อดี | ข้อเสีย | ผล |
|---|---|---|---|
| **i-Duino R3B (UNO-compatible)** | ต่อ PC ผ่าน USB Serial ได้ทันที (Hub สั่งด้วย Python ตาม ADR-0001), สั่ง servo ด้วย PWM ได้ตรงๆ ผ่าน Servo library, เขียน C++ ใน repo เดียวกันและมี CI build ให้แล้ว, เล็กและติดตั้งง่าย | ไม่ใช่อุปกรณ์เกรดอุตสาหกรรม, ไฟ logic 5V และ I/O น้อย, servo ต้องใช้ไฟเลี้ยงแยก | เลือก |
| PLC | ทนทานและเชื่อถือได้แบบงานอุตสาหกรรม, I/O 24V ต่อเซนเซอร์อุตสาหกรรมได้ตรง | servo แบบ hobby ต้องการสัญญาณ PWM ซึ่ง PLC ทั่วไปต้องใช้ output ความเร็วสูงหรือโมดูลเสริม, ต่อกับ Python ต้องตั้ง Modbus/Serial เพิ่ม, เขียนด้วย ladder นอก repo ทำให้ทดสอบอัตโนมัติไม่ได้, ใหญ่และต้องใช้ไฟ 24V, เกินความจำเป็นสำหรับ servo ตัวเดียว | ไม่เลือก |

### 5.5 บรรจุภัณฑ์: **ถุงกระดาษ** แทนกล่อง (ADR-0005)
